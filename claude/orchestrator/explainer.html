The orchestrator kit, explained like you're five

You talk to one chat. Helpers work on tickets in their own rooms. When a helper needs you, it leaves a note, and the chat reads you the notes one at a time. This page walks through every part that makes that happen.

The story in one picture

Imagine a building with a front desk and four workshops.

  • You only ever talk to the front desk, which is the orchestrator chat.
  • Each workshop holds one builder working on one ticket. The workshop is a separate copy of the code, so builders never trip over each other.
  • When a builder hits a question, they stop and slide a note under the door. The building's mail carrier, which is the desktop app, takes the note to the front desk.
  • The front desk keeps the notes in a tray (the queue) and reads you one at a time.
  • You say "B". The front desk walks your answer back to that builder, who carries on.
  • Builders can hand in drafts (draft MRs) whenever they like. Only you can say a draft is final, and then the front desk stamps it "ready".
  • A bouncer (the guard) stands at every workshop's tool cupboard. Dangerous tools stay locked, and builders can only hand in drafts, never final copies.

The cast: every moving part

Each card gives the five-year-old version first, then what it really is and where it lives.

You

The boss

You make the decisions and nothing else. You never open a worker's window. You answer in a word or two, out loud if you like.

Really: you, talking to one desktop session by keyboard or macOS Voice Control.

Orchestrator

The front desk

It takes your requests, hires builders, reads you their notes one at a time, and carries your answers back. It never builds anything itself.

Really: a normal desktop session switched to the Orchestrator output style.
File: ~/.claude/output-styles/orchestrator.md. An output style is part of the system prompt, so it can't be forgotten when the chat gets long and is summarized.

Worker

A builder

One builder per ticket. It works alone. When it needs you, it stops and leaves a note instead of guessing.

Really: a desktop session the orchestrator started with start_session. Its brief tells it to load the ticket-worker skill.
File: ~/.claude/skills/ticket-worker/SKILL.md.

Worktree

A builder's workshop

Every builder gets their own copy of the code, so two builders never mess up each other's work.

Really: a git worktree that the app makes under .claude/worktrees/ on its own branch. The worker renames the branch to Linear's name, for example pasha/fp-412-soft-delete-users.

Desktop app

The mail carrier

It builds the workshops, carries the builders' notes to the front desk, and carries your answers back. It also taps the front desk on the shoulder when mail arrives.

Really: built-in app features: start_session, side-session notes (when a worker ends a turn, the orchestrator gets about the first 400 characters of it and is woken), and SendMessage. No code in the kit does this.

orch

The tray and the sign-in sheet

A sign-in sheet of which builders are hired (with each builder's badge number), and a tray of notes waiting for you.

Really: one bash script that reads and writes small JSON files.
File: claude/orchestrator/bin/orch in dot-files, linked to ~/.claude/orchestrator/bin/orch. Its data lives in a real ~/.claude/orchestrator/ folder (tickets/, queue/, done/), so it never lands in the repo. Only the orchestrator uses it.

Guard

The bouncer

It stands at each builder's tool cupboard and checks every tool before it's used. The first time it sees a new builder, it writes down their badge number, so a builder can't sneak past by changing hats. Dangerous tools stay locked.

Really: a PreToolUse hook that runs before every Bash, Edit and Write call in every session. It stays silent unless the session is a registered worker, which it recognizes by its pinned session ID.
File: claude/orchestrator/hooks/worker-guard.sh in dot-files.

Go

"This draft is final"

Builders hand in drafts. When you say "go", the front desk stamps the draft "ready", and only the front desk can do that.

Really: orch go FP-415 checks that an mr-ready note is waiting, reads its MR number (!1130), and runs glab mr update 1130 --ready. An "ask" permission rule makes the app pop a confirm box first.

Phone ping

The doorbell

When a note arrives and you've walked away, your phone buzzes: "FP-412 needs you."

Really: the PushNotification tool. It reaches your phone when Remote Control is on, and skips itself if you're already looking at the screen.

Installer

The house plans

Every part lives in your dot-files repo, like the rest of your Claude setup, so changes are tracked and you can undo them.

Really: install-mac.sh links the files into ~/.claude/, and claude/settings.json (already linked) registers the hook and rules. Details are below.

A worker's report, up close

This is the note a builder slides under the door. Every part is there for a reason.

FP-412 · question · Should the admin export include soft-deleted users? A) exclude, like the API B) include with deleted_at C) separate ticket. I'd pick B: support uses it for deletion requests.
Ticket first, so you always know what you're answering.
Type: question, approval, blocked, mr-ready or done.
One question, short enough to hear once.
2–4 lettered options, each under 12 words, so you can answer "B".
A recommendation with a reason, so "yes" is also an answer.
Why it has to fit in 300 characters: the app hands the orchestrator only about the first 400 characters of a worker's turn. So the worker puts the whole decision in its wrap_up recap, which is capped at 300. Longer detail goes after it, and the orchestrator can fetch that if you ask "tell me more about 412".

The five report types

TypeLike fiveWhen a worker uses it
question"Which way should I build it?"Scope is unclear, or a choice has real tradeoffs.
approval"I need a grown-up for this part."It needs something dangerous: a DB write, applying a migration, a deploy, a merge, deleting a branch, a prod config change. You do it, or pick another way.
blocked"I'm stuck and can't fix it myself."A check fails for an out-of-scope reason, or the guard stopped it.
mr-ready"My draft is finished. Can it be final?"Lint, format and tests pass, the code review is clean, and everything is pushed to its draft MR. The report names the MR (!1130) and asks for "go".
done"All done! Here's the link."The front desk took the MR out of draft after your go, and nothing is left for the builder to do.

Everything else, such as naming, test layout and small refactors, the worker decides on its own. That's what keeps the tray short.

The queue (the tray of notes)

Each note is one small JSON file in ~/.claude/orchestrator/queue/, named by time, a process number and then the ticket, for example 20261117T091502-48213-FP-412.json. Sorting by name gives oldest first, and the process number keeps two notes from the same second apart.

{
  "ticket": "FP-412",
  "type": "question",
  "text": "FP-412 · question · Should the admin export include …",
  "session": "local_9e0e44a3-…",      ← which worker to answer
  "created": "2026-11-17T09:15:02Z",
  "status": "open"
}

A note's life

open→ you say "next" → presented→ you answer → answered
  • A note you were shown but didn't answer stays presented. It comes back from "next" once nothing newer is waiting, so a skipped note is never lost.
  • superseded: the same worker sent a newer note before you answered, so the old one is set aside. You only ever see a ticket's latest question.
  • closed: you finished the ticket with orch done.

The guard (the bouncer)

Every time any Claude session is about to run a shell command or edit a file, Claude Code first asks the guard script "OK?". The guard answers in three steps:

  1. Do I know this builder's badge? Every call comes with a session ID. If that ID is pinned to a ticket (tickets/FP-412/sessions), it's a builder, whatever branch or folder it's in now. Changing hats doesn't help.
  2. Is this a new builder? If the ID isn't pinned, the guard checks three things: the call comes from an app-made workshop (.claude/worktrees/), the branch names a ticket (fp-412), and that ticket is on the sign-in sheet. If all three hold, it pins the ID. If any is missing, it lets everything through. That's why your own sessions, including one on your main checkout on an fp- branch, are never affected.
  3. Is the tool dangerous? It cuts the command into pieces at ;, &&, | and so on, ignores quoted text and heredoc bodies, and judges each piece by its leading words. If a piece is dangerous, it blocks the call. Technically it exits with code 2, and Claude Code shows the worker the reason. The worker is told: don't work around it, report it.

Try it: would the guard let this through?

This mirrors the real script's rules in the browser, simplified. The script itself is the source of truth.

Why a hook, and not just permission rules? Permission rules match the start of a command, and they're easy to sidestep: git -C . push origin HEAD:qa doesn't start with git push. The guard reads each piece of the command, so it catches that, and it runs even in Auto mode.
It's a backstop, not a lock. It catches honest mistakes. A command hidden inside a double-quoted $(…) gets past it, because quoted text is skipped so commit messages don't trip it.

Go, step by step

Builders push and open draft MRs on their own. "Go" is the one step that's yours: taking the draft out of draft. It has three checks:

  1. The orchestrator checks that the note is mr-ready and that you plainly said go, yes or ship it. It never decides go for you.
  2. It runs ~/.claude/orchestrator/bin/orch go FP-415, always spelled exactly like that. An ask rule in your settings matches that spelling and makes the app pop a confirm box. You say "click Allow".
  3. The script itself refuses unless FP-415's waiting note really is mr-ready and names the MR (!1130). Then it runs glab mr update 1130 --ready. If glab fails, nothing is marked answered.
  4. The orchestrator messages the worker: GO FP-415: !1130 is out of draft and ready for review. Report done and stop.
  5. The worker reports done. Merging is still yours, in GitLab.

A worker can't take its own MR out of draft, because the guard blocks glab mr update --ready, non-draft glab mr create, and glab api.

                                               ├── queue/   one JSON per note
                                               └── done/    finished tickets

claude/settings.json is already linked to ~/.claude/settings.json, so it gets four entries as a normal, reviewable diff:

  • Hook: run worker-guard.sh before every Bash, Edit, Write and NotebookEdit call. It sits next to your existing lint-on-commit.sh hook.
  • Allow rule: Bash(~/.claude/orchestrator/bin/orch *), so the front desk isn't asked permission for every note.
  • Two ask rules: orch go under both the ~/ and the /Users/pasha/ spellings. This is the confirm box for go.

Your first run

  1. Restart the Claude app so it picks up the new style, skill and hook.
  2. Open a session on the repo's main checkout and call it "Orchestrator".
  3. Set Output style → Orchestrator and Permission mode → Auto.
  4. Optional: turn on Remote Control for it, so the doorbell reaches your phone.
  5. Say "start FP-412, soft delete users…".

Traps, and how the kit handles them

Different permission modes make answers stall

Like five: if the front desk and a builder speak different "languages" (permission modes), the mail carrier holds the front desk's letters until you OK each one.

  • Really: SendMessage to a session in a different mode waits for that session's user to approve it.
  • Fix in the kit: workers are started without a permission_mode, so they copy the orchestrator's. Pick Auto for the orchestrator before starting workers.
A permission box inside a worker doesn't ring your doorbell

Like five: if a builder is stuck waiting for someone to click "Allow" in its own room, it hasn't slid a note under the door, so the front desk doesn't know.

  • Really: a note only fires when a worker ends its turn. A permission prompt pauses mid-turn.
  • Fix in the kit: Auto mode plus the guard means most things are allowed or blocked outright, so prompts are rare. "Board" flags a worker that has been running a long time and gives you its link. That's the one time you'd open a worker.
Approvals are yours, not the worker's

Like five: even if you say "yes, use the big saw", the bouncer still won't open that cupboard for a builder.

  • Really: the guard blocks DB writes, migrations and the like even after a yes, by design. Asking a worker to do what the orchestrator itself may not do would sneak around your permissions.
  • So for an approval note, your answers are "I'll run it myself" or "find another way". The orchestrator relays that, and the worker carries on.
Notes pause when you've been away a while

Like five: after a long stack of notes with nobody at the front desk, the mail carrier stops ringing the bell and just leaves the notes in the hall.

  • Really: after many side-session wake-ups in a row with no message from you, the app holds further notes until the orchestrator's next turn, so no phone ping fires.
  • Fix in the kit: on every message from you, the orchestrator first checks for idle workers whose latest report isn't in the tray, and pulls it in. So say anything and it catches up.
  • The tray is plain files, so nothing is lost if the chat gets long and is summarized, or the app restarts.
"Merged" isn't "finished" until the workshop is closed
  • When you say "412 merged", the orchestrator first offers to archive the worker session, which removes its worktree.
  • Only after the archive goes through does it run orch done. Until then the bouncer keeps watching that builder, and it still counts toward the cap of 4.
Too many builders
  • Your attention is the bottleneck, not the builders. orch start refuses a 5th by default.
  • Change the cap with ORCH_MAX_WORKERS. Somewhere between 3 and 5 works best.
Not proven yet (check on your first run)
  • That the app's Output style menu lists styles from ~/.claude/output-styles/.
  • That the "go" confirm box still appears in Auto mode.
  • That the hook input carries a session ID in desktop worker sessions, and that a worker's subagents share it.
  • That renaming the branch inside an app-made worktree doesn't confuse the app.
  • That workers reliably end their turn with a report instead of waiting around.

Glossary

Session
One chat with Claude in the desktop app. The orchestrator is one, and each worker is one.
Turn
One go of Claude working until it stops and hands control back. A worker's report is the end of a turn.
wrap_up
The tool a desktop session calls at the end of a turn. Its "recap" is the short summary the starting session receives.
Side-session note
The app's automatic message to the session that started a worker: about the first 400 characters of the worker's turn.
SendMessage
How one session sends text to another. The orchestrator uses it to deliver your answers.
start_session
The app tool that creates a worker session, its worktree and its branch.
Worktree
An extra checkout of the same git repo in another folder, on its own branch.
Output style
A block of instructions placed in a session's system prompt. It sets how that session behaves for its whole life.
Skill
A packaged set of instructions a session loads when needed. Workers load ticket-worker.
PreToolUse hook
A script Claude Code runs before a tool call. Exit code 2 blocks the call and tells Claude why.
Permission mode
How much a session may do without asking. Auto lets a classifier approve routine actions.
Ask / allow rule
Settings entries that make a command always prompt, or never prompt.
